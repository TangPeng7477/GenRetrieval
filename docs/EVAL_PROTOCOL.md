## 0. TL;DR（一页定版）

| 项 | 定版取值 | 依据 |
|---|---|---|
| **数据源** | 官方 `benchmark/5core` 三段（train/valid/test）合并成每用户时间序列 | `DATASET.md §4` |
| **划分** | **plain leave-one-out（LOO）**：每用户序列按时间排序后，**test = 最后一条、valid = 倒数第二条**；train = 前 K−2 条的滑动窗口 | `scripts/data/prepare_amazon23_loo.py`；与 TIGER / LETTER / LC-Rec / IDGenRec / CCFRec / MTGRec / EAGER 同构（7/8 同类目） |
| **train** | 滑窗样本：第 i 个物品为 target，前 ≤20 个为 history（k ∈ [3, K−1]） | `prepare_amazon23_loo.py:75` |
| **valid** | 每用户 **1 条**：前 K−2 个物品（≤20）→ 预测**倒数第二条** | `prepare_amazon23_loo.py:80` |
| **test** | 每用户 **1 条**：前 K−1 个物品（≤20）→ 预测**最后一条** | `prepare_amazon23_loo.py:84` |
| **候选集** | **全库**（I&S 25,848 ／ VG 25,612），全量排序，**无负采样** | 与 LC-Rec / IDGenRec / CCFRec 一致 |
| **屏蔽集** | test 阶段 history（含 valid 目标）+ **完整训练序列** | `baseline/README.md §2.2` |
| **主指标** | **HR@10** | 三方公共交集，见 §3.1 |
| **选型指标** | **NDCG@10**（早停 + 选 ckpt） | 位次敏感 |
| **辅助必报** | HR@1/5、NDCG@5、MRR、coverage@10、gini@10 | §3.2 |
| **生成式专用** | `beam_ceiling@K`、`exp(−valid_ce)`；**MRR 对 sid_gr 无意义**（候选集=beam，已在表内标 n/a） | §3.4 / README 踩坑 B-08 |
| **模型选择** | valid 的 NDCG@10 早停（`sid_gr` 用 valid 的 teacher-forcing CE） | test 只报数，绝不参与选择 |

**一句话**：本协议 = **plain LOO + sliding-window train**，是当前 Amazon 生成式推荐论文 7/8 同类目（TIGER / LETTER / LC-Rec / IDGenRec / CCFRec / MTGRec / EAGER）的标准做法。**唯一不能做的是拿绝对值和论文横比**——它们的 protocol 跟我们一致但实现细节（hist 长、5core/0core、屏蔽与否）仍有差异（§1.3）。

**已知代价（诚实边界）**：

1. **冷启动命题从主榜消失**：5core 强制每个 test 物品 ≥5 次交互，LOO 取每用户最末条 → **几乎所有 test 目标都在 train 历史里出现过**。
   v1 的"31% / 49% 冷启动占比"与"内容派生 SID 在冷目标达 80% / 94% 热目标水平"这两条发现**整列消失**。
   切到 LOO 是因为想与论文对标；冷启动命题则改在 `MiniOneRec-style sliding-window time-split` 附录里单独跑（§6 待办）。
2. **数据泄漏论据**（Ji TOIS'23 / Meng RecSys'20）：LOO 有数据泄漏会让模型相对排名不可信 → 这一点本项目**已知并接受**，作为对齐 CCFRec/MTGRec 的代价。

## 1. 数据集划分（定版 = LOO）

### 1.1 为什么是 plain LOO

三个理由，按权重排：

1. **能与同类目论文对齐**：CCFRec / MTGRec / TIGER / LETTER / LC-Rec / IDGenRec / EAGER 7/8 都用 LOO（实测 I&S 数据集统计逐格相同：50,985 用户 / 25,848 商品）—— 唯一允许横向比较的路径。
2. **实施清晰、可复现**：每用户一条 valid + 一条 test + sliding-window train，无任何"段内残余"歧义。
3. **与最新生成式开源框架同源**：MiniOneRec（arXiv:2510.24431）的切分 **也是全局时间**（**不是 LOO**，我们之前误写过），但其代码里的 sliding-window 思路与本项目 LOO 的 train 部分同源。

⚠️ **但评估样本粒度不同**：MiniOneRec 的 valid/test 是**逐条滑窗**（每用户多条），本 LOO 只取**倒数第 2/倒数第 1**（每用户 1 条）。
是否扩展到 MiniOneRec-style 见 §6 待办。

### 1.2 划分的实测规模（面试必须能背）

| | IandS | VG |
|---|---:|---:|
| 原始分片 · 交互数 train / valid / test | 297,922 / 44,128 / 70,897 | 736,827 / 34,510 / 43,249 |
| **LOO 样本数 train / valid / test** | **208,999 / 50,984 / 50,982** | **435,534 / 94,761 / 94,759** |
| 建模物品空间 `n_items` | **25,848** | **25,612** |
| 建模用户空间 `n_users` | **50,985** | **94,762** |
| valid/test 每用户样本数 | 恒 1（plain LOO） | 恒 1 |

- **训练样本数 ≈ Σ_u (L_u − 2)**，由 LOO 序列长度决定；valid/test **每用户 1 条**，由用户数决定。
- `n_users` = 50,985 / 94,762 = 官方 5core 用户全集（K≥3 全部保留，与 K≥3 用户数一致）。
- `n_items` 比 v1 多 1：v1 过滤掉无 title 的 1 个物品，但 LOO 用的 .inter 只受 5core + min_rating 约束 —— `B08963HYLV` / `B017VLXJ7G` 等无 title 物品在 .inter 中依然有 id（由 `item2id` 提供），可以被预测。这是 v1→v2 的统计差异，不影响对比（同一 LOO 协议下内部一致）。

### 1.3 与另两套协议的关系（**唯一合法用法是组内排序**）

| 维度 | 主流论文（CCFRec / MTGRec / TIGER / LC-Rec） | 官方参考实现（BLaIR / RecBole） | **本项目（v2）** |
|---|---|---|---|
| core 过滤 | 5core | **0core** | **5core** |
| 切分 | **`last_out`（LOO）** | `timestamp` | **`last_out`（LOO）** |
| I&S 候选空间 | 25,848 | **427,500**（16.5×） | 25,848 |
| VG 候选空间 | 25,612 | **137,200**（5.4×） | 25,612 |
| 历史截断 | 20 | **50** | **20** |
| 指标 | R@5/10、NDCG@5/10 | [Recall, NDCG] × topk [10, 50] | HR@1/5/10、NDCG@1/5/10、MRR、coverage、gini |

**三套口径两两都不能横比**：我们与同类目论文「切分同、core 同、hist 同」→ **可量级对齐**；与官方参考实现「core 不同、hist 不同」→ 不可横比。
→ 逐项对照与原文引用见 **`baseline/SURVEY.md §1.5.2`**。

> 唯一需要警惕：CCFRec / MTGRec **在公开数据上**用 5core + LOO，跟我们协议**完全相同**，所以**绝对值可以做量级参照**（不能直接横比，但能确认是否在同一梯队）。

## 2. 样本构造与候选集（定版）

### 2.1 train 样本（sliding-window on K−2 items）

对每用户的整条序列（合并 train/valid/test 三段、按 timestamp 升序、按 asin 去重保留最早一次），设长度 K。

- 对 k ∈ [3, K−1]：
  - target = uniq[k−1] 的 asin
  - history = uniq[max(0, k−1−20) : k−1]（最近 ≤20 个）
- 滑动窗口产出 K−3 个样本。

### 2.2 valid / test 样本（plain LOO）

| split | history | target | 样本数 |
|---|---|---|---|
| valid | 前 K−2 个物品（截断 20） | 倒数第 2 条 uniq[K−2] | 每用户 1 条 |
| test | 前 K−1 个物品（截断 20） | 最后 1 条 uniq[K−1] | 每用户 1 条 |

实测（`scripts/data/probe_sequence_reconstruction.py` 探针逻辑可复用）：

- I&S test 每用户样本分布 = `{1: 50,985}`；VG 同。
- history 长度分布：min=2（K=3 的用户），max=20；20 对应 K ≥ 22 的用户，被截断。

### 2.3 候选集与屏蔽集

- **候选集 = 全库**（所有 `n_items` 个物品），逐条样本做全量排序。**不做负采样** —— 与官方参考实现一致，也是能报"绝对能力"的唯一方式。
  > **为什么一旦选择"全库排序"，就必须屏蔽已交互物品？** 候选是"全库"时，"推荐用户自己看过的物品"
  > 就成了一次**无意义的命中**；不屏蔽的话所有模型都能靠"背历史"白刷分，而且
  > **ID 类方法（`pop` / `itemknn` / `sasrec`）占便宜最大** → 会系统性高估全部基线。
  > 生成式方法（MiniOneRec / GRID）**不屏蔽**，是因为它们评估时候选 = **模型自己生成的 beam**、
  > **不做全库排序** —— **"全库排序"与"屏蔽已交互"是绑在一起的一对**。
  > 核实过程（含 MiniOneRec 源码与实测）见 `baseline/SURVEY.md §1.5.3`。
- **屏蔽集**（排序前置 `-inf`）= 该条 `history`（含 valid 目标）∪ 该用户**重建出来的完整训练序列**。

**为什么必须重建完整训练序列**：`train.inter` 只落盘滑窗样本，history 被截断到 20。
若只用文件里的 history 做屏蔽，用户第 21 个以前的训练物品会**留在候选集里**，模型只要学会"推荐用户很久以前看过的东西"就能白刷分。

```
tr = [第一个样本的 history[0]] + [各样本的 target]（按文件顺序）
```

三条前提均已逐条实测通过（脚本 `baseline/scripts/probe_sequence_reconstruction.py`）：

| 前提 | 实测 |
|---|---|
| ① 首样本 history 长度恒为 1 | I&S 50,985 / VG 94,762 个用户**全部**为 1 ✅ |
| ② 重建序列能还原 valid 输入 `train_seq[-20:]` | 重建可还原 ✅ |
| ③ K < 3 的用户被 K≥3 过滤器丢弃，残余归零 | LOO 协议要求 K≥3，5core 保证 K≥5，**无残余** ✅ |

> LOO 协议下"不可屏蔽项残余"为 **0**（v1 timestamp 协议下 I&S 0.249% / VG 0.106% 的残余**结构性消失**）。

### 2.4 已知残余（诚实边界，必须一起讲）

1. **LOO 的固有数据泄漏**（Ji TOIS'23 论证）：切分采用每用户末条，模型可能见过目标之前的近邻交互，导致 HR@K 被结构性高估。
   本项目**已知并接受**（§1.4）—— 同协议下所有 baseline **共享这份偏差**，组内排序可比，绝对值与论文只能量级参照。
2. **同分平局**：`rank = #{score > score_target} + 1`，同分取最优位次（与随机打破平局的期望一致，且可复现）。
3. **`valid/test` history 含 valid 目标**：这是 LOO 标准做法（second-to-last 在 test history 里），不构成额外泄漏 —— v1 timestamp 协议里 valid 段所有物品都进 history，与 LOO 等价。

## 3. 指标（定版）

### 3.1 主指标 = HR@10，唯一实现 `baseline/common/metrics.py`

**为什么是 HR@10 而不是别的**：

| 理由 | 说明 |
|---|---|
| 三方公共交集 | CCFRec 报 R@10、MTGRec 报 R@10、官方参考实现 topk 含 10 → **K=10 是唯一三方都有的档位** |
| 单正样本下等价 | 每样本 1 个目标 ⇒ **HR@K ≡ Recall@K ≡ Hit@K**（命名不同、数值相同），所以引用文献的 R@10 时不存在换算问题 |
| 判据最直观 | "能不能把目标召进前 10" 就是召回层的本职；SFT/RL 的三条闸门（§5）全部用它 |

### 3.2 全套指标定义（公式）

```
HR@K      = 1/U · Σ_u 1[ rank_u ≤ K ]
NDCG@K    = 1/U · Σ_u 1[ rank_u ≤ K ] / log2(rank_u + 1)      # 单正样本 ⇒ IDCG = 1
MRR       = 1/U · Σ_u 1/rank_u                                # 未命中记 0
coverage@10 = |{ top-10 里出现过的不同物品 }| / n_items
gini@10     = top-10 推荐频次的 Gini 系数（越大越集中、越偏头部）
rank_u    = #{ score > score_target } + 1                     # 1-based，同分取最优位次
```

- **HR/NDCG 必报**：HR@1/5/10、NDCG@1/5/10 —— 只看 @10 会掩盖位次分布（"挤进第 10 名"和"排在第 1 名"在 HR 上同分）。
- **coverage / gini 必报**：本项目特有（V0 pipeline 没有），用于观察流行度偏置。
- **MRR 必报**：整体排序质量，对少数"命中很远"的样本不敏感。
- 与项目既有实现的对齐：`utility.py:calculate_hit`；**后续 SFT/RL 必须 import 同一实现**，否则"生成式比 baseline 强多少"这句话不成立。

### 3.2.1 `coverage@10` / `gini@10` 详解（推荐广度与集中度）

> 实现：`baseline/common/metrics.py::coverage_metrics`，**唯一实现**，与 HR 同一次 `evaluate` 内产出。

**一句话**：把所有用户的 top-10 推荐列表摊平，数里面出现过多少个**不同**的物品，再除以物品总数。

```
coverage@10 = |{ top-10 列表里出现过的不同物品 }| / n_items
```

它回答的是**"这个模型能触达多少物品"**，而不是"推得准不准"——这是两个正交的维度。

**实测直观对照**（IandS，n_items = 25,847）：

| 模型 | coverage@10 | 折算覆盖物品数 | 含义 |
|---|---:|---:|---|
| `content_ann` | 0.8748 | ≈ 22,611 | 几乎覆盖全库 |
| `twotower_mm` ⚠️已移出主榜 | 0.0766 | ≈ 1,980 | 集中在约 8% 的物品（仅作 coverage 偏低的示例，见 §4.1.1） |
| `pop` ⚠️已移出主榜 | 0.0007 | ≈ 18 | **所有人拿到同一份 top-10** |

**必须与 HR 一起读，单独看没有好坏**：

|  | coverage **高** | coverage **低** |
|---|---|---|
| **HR 高** | ✅ **又准又多样**（理想） | ⚠️ 准但集中：只推少数物品，长期看有"信息茧房"风险 |
| **HR 低** | ⚠️ 多样但不准：近似随机撒网 | ❌ 又差又集中（最糟） |

所以 `twotower_mm`（HR 0.0322 > content_ann 0.0288，但 coverage 0.0766 ≪ 0.8748）
属于**"更准但更集中"**——是真实的 trade-off，不是缺陷。

**配套指标 `gini@10`**：top-10 推荐频次的 **Gini 系数**（越大越集中、越偏头部）。
它与 coverage 互补：coverage 量"广度"（覆盖了多少不同物品），gini 量"分布"（推荐次数有多不均）。
两者结合才能分清"推荐了很多样"与"推荐得均匀"这两种不同的好。

**一个重要用途：识别退化解**。`coverage@10` 异常低（< 0.05）是"模型输出退化成常数"的
**唯一可靠线索** —— 因为此时分数是有限值，NaN 检查拦不住，而 HR/NDCG/MRR 会假性报 1.0。
详见 §4.3。

### 3.3 冷 / 热分桶 HR@10（v2 下几乎不可报）

**v2（LOO）下分桶**：按"目标商品是否在 train.inter 里出现过"分桶。但 LOO + 5core 几乎保证目标在 train 历史里出现过，**冷桶样本数 ≈ 0**，该指标 **HR@10 退化**为"评估实施是否泄漏"的自检而非模型差异。

**保留位置但置 ⏸ 待办**：冷启动命题改在 §6 待办 `MiniOneRec-style sliding-window time-split` 附录里单独跑。

### 3.4 生成式专用指标

| 指标 | 定义 | 为什么必须有 |
|---|---|---|
| `beam_ceiling@K` | 目标物品的 SID 是否出现在生成的 top-K SID 里 | 这是**解码上限**，不是成绩。beam 宽度直接卡住 HR@K 的天花板；把"模型不会生成"与"beam 太窄"分开 |
| `exp(−valid_ce)` | teacher-forcing 验证困惑度的指数 | **校准读数**。若 ≈ `beam_ceiling`，说明模型校准良好但不够准（信息在 SID 里、输在生成器） |
| **MRR ⚠️** | 对 `sid_gr` 无意义 | 候选集 = beam 内 SID 映射出的 ~20 个物品，**MRR ≈ 1/beam 宽度**是结构常数。已在 `RESULTS.md` 标 `n/a`（README 踩坑 B-08） |

**双域 v2 LOO 实测**（2026-09-13，修复 `range(3,K)` off-by-one 后，16/16 全部跑完）：

| 域 | `beam_ceiling@20` | `HR@10` | `exp(−best_valid_ce)` | **MRR（实测）** | `1/beam = 0.05` |
|---|---:|---:|---:|---:|---:|
| IandS | 0.0312 | 0.0168 | 0.0452（ce=3.0987） | **0.0506** | 0.05 |
| VG | 0.0641 | 0.0354 | 0.0524（ce=2.9492） | **0.0555** | 0.05 |

三个读法（每条都双域互证）：

1. **MRR ≈ 1/beam 的"结构常数"理论被实测钉死** —— 实测 0.0506 / 0.0555，对照 `1/20 = 0.05`，
   两域都落在 1~11% 内。这确认 README 踩坑 B-08 的判断：**`sid_gr` 的 MRR 不携带排序质量信息，禁止用于横向比较**。
   （注意 VG 的 0.0555 甚至略高于 sasrec 的 0.0493 —— 这正是陷阱所在：数字"好看"但无意义。）
2. **`beam_ceiling / HR@10 ≈ 1.8`，两域一致**（IandS 1.86、VG 1.81）——见下方插入§3.4.1 的专项诊断。
3. **`exp(−ce)` 系统性高于 `beam_ceiling`**（0.0452 vs 0.0312、0.0524 vs 0.0641）——
   模型对"下一个 SID"的**校准概率**高于它**实际能生成出来**的比例，这是自回归解码损耗的直接证据。

### 3.4.1 `beam_ceiling / HR@10 ≈ 1.8` 说明了什么（2026-09-13 补）

配置约束：`beam=20`、`topk_eval=10`。若目标 SID 已落在生成的 20 个候选里，
但它在 beam 内的排序位次是**均匀随机**的，则它进入前 10 的概率 = `10/20 = 0.5`，
此时 `beam_ceiling / HR@10` 应恰好为 **2.0**。

**实测 1.86 / 1.81，双域一致地略低于 2.0** ⇒ 结论：

> **beam 内部的排序质量仅比随机好一点点（约 7~10%）。**
> 当前 `sid_gr` 的有效信号几乎全部来自"能不能生成出来"（`beam_ceiling`），
> 而"生成出来后排第几"几乎是在碰运气。

这对 SFT/RL 阶段是一条**极强的正向路由指示**：
- 若下一代只优化生成器（更多 epoch / 更大 beam），收益上限被 `beam_ceiling` 牢牢锁住；
- **真正的增益空间在 beam 内的重排序（rerank）**：一旦把 beam 内排序从"≈随机"提到 sasrec 的水平，
  在 ceiling 不变的前提下 HR@10 理论上还有接近 **2×** 的 headroom。
- 已写入 `§6 待办`：为 `sid_gr` 加一层 beam-internal scorer（与 `EVAL_PROTOCOL §3.4.1` 互指）。

> 通用教训（`SURVEY.md §5 坑 4`）：**看到生成式论文的 R@K，先问"候选集是什么"**。
> GRID（CIKM'25）的 `Recall@10` 本质就是本表的 `beam_ceiling@10`（候选 = 模型自己生成的 SID），**不是全库排序**。

### 3.5 K 值的取法（本轮定版）

- **本轮固定 K ∈ {1, 5, 10}**：K=10 是三方公共交集；K=5 对齐文献；K=1 看"榜首命中率"。
- **本轮不报 K=50**：官方参考实现的 topk 含 50，但它跑 0core（候选大 5~16×），K=50 的语义与我们的 25k 候选空间不可比。
- **工程改进（供下一轮）**：评估时把 `ranks` 存盘（`ranks_test.npy`），这样以后改 K 不用重训。
  本轮产物**没有存 ranks**，因此 K 值表已固定 —— 要扩 K 必须重跑。

### 4.1.1 双塔 baseline：原理、输入与「时序建模 / 内容投影」的价值量化（2026-09-13 新增）

实现：`baseline/models/two_tower.py`。与序列模型（GRU4Rec / SASRec）的**唯一结构性差别是
用户塔不做时序建模**（历史仅做 mean 池化），因此可把"建模范式的贡献"单独摘出来。

#### ① 什么是双塔（Two-Tower / DSSM 范式）

```
用户塔：  历史物品 ──[聚合]──> MLP ──> 用户向量 u   (b, 64)
物品塔：  每个物品 ───────────> MLP ──> 物品向量 V   (n_items, 64)
                        打分 = logit_scale · (u @ Vᵀ)
```

工业界（YouTube DNN / 百度 / 阿里召回）的主流形态，核心价值是
**两侧向量可分别离线预计算**，在线只需一次 ANN 检索，延迟与物品量无关。

⚠️ **两侧塔必须落在同一向量空间，内积才有意义**。本项目通过"两侧共用同一个物品表示函数"
来保证这一点（id 版共用 `item_emb`，mm 版共用 `feat_mat` + `proj`）。

#### ② 两个版本的输入与结构

| | `twotower_id`（A_classic） | `twotower_mm`（B_retrieval） |
|---|---|---|
| **用户塔输入** | 历史物品 **ID** 序列（左填充 maxlen=20）→ 查 ID embedding | 历史物品 **ID** → 查融合向量表（**冻结**） |
| **物品塔输入** | 物品 ID → 查**同一张** ID embedding | 物品 ID → 查**同一张**融合向量表 |
| **物品表示来源** | `nn.Embedding(n_items+1, 64)`，**随机初始化后学出来** | `emb_fused_gate_e60.npy`（Qwen3-Embedding + SigLIP 门控融合，1024 维） |
| **投影** | 无（embedding 本身就是 64 维） | `Linear(1024→64) + LayerNorm`（可训练） |
| **聚合** | 历史 mask-mean 池化（pad 位不计入） | 同左 |
| **两侧 MLP** | `Linear→LayerNorm→ReLU→(Dropout)→Linear→LayerNorm` | 同左 |
| **打分** | `logit_scale · (u @ Vᵀ)`，`logit_scale` 可学习（初值 10） | 同左 |
| **参数量** | **1.67M**（其中 `item_emb` 占 1.64M ≈ 98%） | **82K**（`proj` 65K + MLP ~16K） |
| **新物品** | ❌ embedding 仍是随机噪声，推不动 | ✅ 有内容即可算出向量 |

关键实现细节（都是踩坑后加固的，不要简化掉）：

- **融合向量先做 L2 归一化再投影** —— 与 `content_ann` 口径一致，保证"学投影 vs 直接用"是可比对照。
- **`proj` 后与两侧 MLP 收尾各加 `LayerNorm`** —— 1024→64 的裸线性层在 lr=1e-3 下会梯度爆炸
  （实测 VG 第 11 轮 `train_loss=731`），爆炸后 ReLU 全部死亡、输出退化成常数（详见 §4.3）。
- **`logit_scale` 不可省** —— 两侧 LayerNorm 后内积 ∈[-1,1]，直接喂 softmax 会因 logits 过小而学不动。
- **训练目标统一全库 softmax**（不用工业界的 sampled softmax / BPR）—— 与 `models/seq.py` 口径一致，
  这样 `twotower_id` vs `sasrec` 的差距**只能归因到"是否建模时序"**，不掺损失函数的混杂。

#### ③ 价值量化（双域实测）

| 对照 | IandS | VG | 读法 |
|---|---:|---:|---|
| `twotower_id` → `gru4rec` | 0.0345 → 0.0361（**+4.6%**） | 0.0740 → 0.0871（**+17.7%**） | GRU 时序建模值多少 |
| `gru4rec` → `sasrec` | 0.0361 → 0.0395（**+9.4%**） | 0.0871 → 0.0971（**+11.5%**） | 自注意力比 GRU 强多少 |
| **池化 → 自注意力（合计）** | 0.0345 → 0.0395（**+14.5%**） | 0.0740 → 0.0971（**+31.2%**） | **时序建模的总价值** |

**结论 1（主榜内，仍然成立）**：**时序建模的收益在 VG 上更大**（+31.2% vs IandS +14.5%）——
VG 交互更密，行为先后顺序携带的信息更多；IandS 稀疏，历史更接近"一个兴趣集合"，池化损失就小。

**结论 2、3（`twotower_mm` 已于 2026-09-14 移出主榜，结论保留备查）**：

| 对照 | IandS | VG | 读法 |
|---|---:|---:|---|
| `content_ann` → `twotower_mm` | 0.0288 → 0.0322（**+11.8%**） | 0.0237 → 0.0661（**+178.9%**） | **学投影比直接用原向量强多少** |
| `twotower_mm` / `twotower_id` | 0.933 | 0.893 | 多模态版达到 ID 版的百分比 |

- **学出来的投影远比直接用融合向量检索有效**，VG 上尤其显著（**+178.9%**）。
  这修正了此前"学投影≈直接用"的判断——那是**退化解造成的假象**（见 §4.3）。
  含义：融合向量虽好，但它是**通用语义空间**，直接余弦检索并不对齐"下一个购买"这个任务；
  投影层把它们拉到了任务相关的度量空间。
- **多模态版用 1/20 参数达到 ID 版 ~90% 的效果**（82K vs 1.67M），
  且**新物品只要有内容就能算出向量** —— 这是它相对纯 ID 路线的核心价值。
- ⚠️ 移出主榜的原因：指标低于 `content_ann` 之外未能提供增量对照价值，
  且 `coverage@10` 偏低（0.0766 / 0.2106 vs content_ann 的 0.87/0.86），打分分布过于集中。
  实现类 `TwoTowerMM` 保留，产物归档在 `baseline/_dropped/2026-09-14_cut_twotower_mm/`，
  registry 取消一行注释即可加回。

### 4.3 🔴 退化解让指标假性报 1.0（2026-09-13 踩坑，必读）

**现象**：`VG/twotower_mm` 首轮跑出 `HR@10=1.0000 / NDCG@10=1.0000 / MRR=1.0000`，
同时 `coverage@10=0.0048`（异常低）。

**根因链**（查训练曲线确认，非推测）：

```
epoch 7   train_loss=8.29   valid HR=0.0540    正常收敛
epoch 11  train_loss=731.85  ← 梯度爆炸
   ↓ 参数极端化 → ReLU 全部死亡 → 输出退化为常数
   ↓ 全库候选同分 → (scores > tgt_score) 全 False → rank 恒为 1
   ↓ HR@10 / NDCG@10 / MRR 全部假性 = 1.0
```

**为什么没被拦住**：分数是**有限值**（常数），`common/nn.py` 里 `np.isfinite` 的
NaN/Inf 检查对这种情况**完全无效**。唯一线索是 `coverage@10` 低到离谱。

**已做的两处修复**：

1. `common/nn.py::evaluate` 增加**通用退化检测**：行内 std < `1e-6` 直接 raise，
   对所有模型生效，杜绝任何假 1.0 进结果表。
2. `models/two_tower.py`：`proj` 后与两侧 MLP 收尾各加 `LayerNorm`，
   并引入可学习 `logit_scale`（初值 10）。两侧归一化后内积 ∈[-1,1]，
   不乘 scale 会因 logits 过小而学不动。

**修复效果**：`twotower_mm` VG 从 1.0000（假）→ **0.0661**（真）；
IandS coverage 从 0.0266 → 0.0766；训练 loss 全程单调下降，不再有跳变。

> **通用判据（写进红线）**：看到 HR/NDCG/MRR **同时**接近 1.0，或 `coverage` 异常低（<0.05），
> **先怀疑退化解，不要以为模型太强** —— 去看训练曲线里 `train_loss` 有没有跳几个数量级。

### 4.2 `sid_prefix` 的证伪诊断（2026-09-13，回答"0.0545 是不是虚高"）

> 起因：`sid_prefix` HR@10 = 0.0545（IandS）看起来比所有经典 baseline 高一倍，质疑是否虚高。
> **结论：不是 bug / 不是泄漏，但有两点必须写清楚。** 复现脚本 `baseline/scripts/diag_sidprefix.py`。

**① placebo 测试 —— 决定性证据（双域一致）**

把 `sid_raw.npy` 的**行随机打乱**（破坏"物品 ↔ SID"的对应关系，但每层码的出现频次完全不变），其余一律照旧：

| 变体 | IandS HR@10 | VG HR@10 | 说明 |
|---|---:|---:|---|
| baseline（原样） | **0.0545** | **0.0627** | 正式主榜数字 |
| `shuffle_item` | **0.0113** | **0.0047** | ⬇ **4.8× / 13.3×**，且**低于 pop**（0.0174 / 0.0249） |
| `random_sid`（全随机 3 层码） | 0.0153 | 0.0064 | ⬇ 同上 |

→ **若高分来自 bug / 泄漏 / 屏蔽失效，打乱 SID 不会改变任何东西。** 实测崩到连流行度兜底都不如，
证明 0.0545 **100% 来自 SID 的语义结构**。**此项彻底排除实现问题。**

**② 相邻性红利 —— 质疑中被证实的部分**

统计 target 与 history 倒数第 j 条**共享第 l 层码**的比例，并给出"target vs 随机物品"对照：

| 位置 | 第 1 层（IandS / VG） | 第 2 层 | 第 3 层 | 随机对照（第 1 层） |
|---|---:|---:|---:|---:|
| `h[-1]`（最后一条） | **3.71% / 6.51%** | 0.80% / 0.73% | 0.55% / 0.48% | 0.47% / 0.61% |
| `h[-3]` | 2.48% / 4.72% | 0.58% / 0.55% | 0.44% / 0.41% | 0.42% / 0.65% |

→ target 与最近一条历史**共享粗粒度语义区（第 1 层）的概率是随机的 7.9×（IandS）/ 10.7×（VG）**。
**相邻购买确实倾向落在同一语义区，`sid_prefix` 在吃这个红利 —— 这点质疑成立。**
但**绝对值很小**：93~96% 的情况下 target 与 h[-1] 连第 1 层都不共享，
所以它不是粗糙的"猜同类目"，红利有限。**这是 LOO 协议的固有属性，不是 sid_prefix 独有的作弊。**

**③ 意外发现 —— 当前 `maxlen=20` 是次优配置**

history 长度消融（屏蔽集仍为完整历史，纯粹让模型**看到的信号变少**）：

| 只看最后 k 条 | IandS HR@10 | VG HR@10 |
|---|---:|---:|
| k=1 | 0.0370 | 0.0562 |
| **k=3** | **0.0626** ⭐ | **0.0697** ⭐ |
| k=5 | 0.0606 | 0.0660 |
| k=10 | 0.0546 | 0.0637 |
| k=20（当前定版） | 0.0545 | 0.0627 |

→ **历史不是越长越好**：1→3 条递增，**3 条达峰**，之后久远历史成为噪声把分数摊薄。
双域一致地显示 `k=3` 比 `k=20` **高 11~15%**（IandS +14.9%、VG +11.2%）。

⚠️ **但主榜暂不改成 k=3**，理由（必须写明，避免事后被质疑调参）：
1. **口径可比性**：主榜所有模型统一 `maxlen=20`（TIGER / LC-Rec / LETTER / EAGER / CCFRec / MTGRec 一致），单独给 sid_prefix 开小灶会破坏"共用同一份输入"的前提；
2. **过拟合风险**："最后 3 条"针对 LOO 的"最后一条 target"这个**特定位置**做了优化，换到 v3 MiniOneRec-style 协议是否成立**未经验证**；
3. 因此这里只作为**已知可调优空间**记录，留待 v3 附录与 k∈{3,5} 的多协议验证一起做。

## 5. 给 SFT / RL 的三条闸门（建议写死为验收标准）

> ⚠️ **2026-09-13 重设**：`sid_prefix` / `sid_gr` 已移出对比矩阵，原闸门 1（HR@10 > sid_prefix）
> 与闸门 3（beam_ceiling）的锚点随之失效。新标准以 **`sasrec`** 为主锚 —— 它是精简后主榜里
> **最强的有监督经典序列模型**，用它当达标线，"生成式召回有效"这句话才站得住。

按顺序全部通过，才允许对外说"生成式召回有效"：

1. **HR@10 > `sasrec`**（当前主榜最强经典序列模型，v2 LOO I&S **0.0395** / VG **0.0971**）——
   这是核心闸门。注意 **VG 的 0.0971 是个硬门槛**：它已超过论文里 MTGRec 在 Amazon2023 上
   复现的 TIGER（VG 0.0868），要在 VG 上打赢它并不轻松。
2. **HR@10 > `content_ann`**（融合向量直接近邻检索，I&S 0.0288 / VG 0.0237）——
   回答"量化成 SID 再生成"是否比"直接用融合向量检索"更值，即语义信息是否真被用上。
3. **与论文锚点量级对齐**：I&S ≥ **0.0422**（TIGER，MTGRec 在 Amazon2023 上复现）、
   VG ≥ **0.0868**；若能到 MTGRec 的 0.0506 / 0.0956 则属第一梯队。
   （文献数字只作外部参照、不作硬门槛 —— 口径仍有差异，见 §4.1。）

前置条件：SFT/RL 必须复用**同一份 `EvalSet`**（同样的 history、同样的屏蔽集）与 `common/metrics.py` 的同一实现。

**旧闸门留档（说明为什么作废，避免后人误用）**：

- 旧闸门 1「HR@10 > sid_prefix」：sid_prefix 虽经 placebo 测试证明其分值来自 SID 语义结构
  （§4.2①，打乱后崩到 0.0113/0.0047），但吃到 LOO 的"相邻购买同语义区"红利（§4.2②），
  且 maxlen=20 并非其最优配置（§4.2③），**口径不干净 ⇒ 不宜当达标线**。
- 旧闸门 3「beam_ceiling 显著高于 HR@10」：随 `sid_gr` 一并移出主榜。
  但该诊断结论仍保留在 **§3.4.1**，对未来任何生成式模型依然适用
  （它指出瓶颈在 beam 内排序而非 beam 宽度，ceiling 不变时理论还有近 2× headroom）。
