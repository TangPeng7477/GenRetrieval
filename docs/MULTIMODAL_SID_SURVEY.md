> 调研时间：2026-09-12

## 0. 一句话结论

2026 年工业界的多模态 SID 已经收敛出一条**共同骨架**：

```
多模态 embedding（各自的 encoder）
  → 融合成单一向量
  → RQ（残留量化）成层级离散码
  → LLM 自回归生成
```

但**融合层的位置**和**碰撞处理策略**上，三家头部公司给出了三种不同的答案，
其中**快手 AdaSID 的发现与我们在 M2 实测到的现象完全吻合**（见 §5）。

## 2. 四种主流范式对比

### 2.1 PLUM / YouTube — "融合即投影 + 对比正则进量化器"

**SID-v2 的四项增强**：

1. **Fused Multi-Modal Content Representation**
   M 个异构 embedding `{x_m}`（视频/音频/文本元数据）各经独立 encoder `E_m` → 得 `z_m`
   → **concat 成 `z̃ = [z_1,…,z_M]`** → 投影成单一向量 `z`

2. **多分辨率码本（Multi-Resolution Codebooks）**
   不是均匀分辨率。第 `level` 层的码本大小 = `2048 / 2^(level-1)`
   → level1 = 2048，level2 = 1024，level3 = 512 …
   动机：浅层码字要有强区分力，深层码字只编码低熵残差。

3. **Progressive Masking**
   训练时随机取前 `r` 层（`m_l = 1{l < r}`），强制层级更严格、更可解释。

4. **共现对比正则（关键）**
   `L = L_recon + L_rq + L_con`
   其中 `L_con` 是共现正样本的 InfoNCE：
   `L_con = -1/(2N_b) Σ log[ exp(sim(p_i, p_i⁺)) / Σ_j exp(sim(p_i, p_j)) ]`
   **直接加进 RQ-VAE 的训练目标**，把协同信号注入 tokenization 过程。

**线上结果**：Shorts Panel CTR **+4.96%**；CPT 用了约 **260B tokens**；
模型 110M–3B activated 参数（Gemini-1.5 MoE 家族）；
900M MoE 达到收敛时 FLOPs **< 0.55x** 基线；有效词表扩大 **13.2x**。

> **对我们最关键的启示**：PLUM 把对比损失加在**量化器**上，而不是先训一个独立的融合网络再喂 RQ。
> 我们当前是"两阶段分离"，这是一个明确的升级点（见 §6.1）。

### 2.2 FORGE / 淘宝 — "SID 构建策略的基准 + 免训练评估"

**核心贡献**：系统研究 SID 构建的各个自由度，并给出**不需要跑 GR 训练**的评估指标。

**码本结论**（来自论文消融）：
- 默认 **3 层 × 8192** 效果最好
- `1024_4096_32768` 组合能提升 HR@1000
- RQ-VAE 是最合适的 tokenizer（对比其他方案更优或持平）

**两个新评估指标**：`embedding hitrate` + `Gini coefficient`
—— 与下游推荐效果高度相关，**免去昂贵的 GR 训练**。

**其他自由度**：KNN 碰撞阈值 σ = 25（base）/*10*/*5*，动态 beam size {300,600,1200}。
论文自评指出这些是手工选定的，**缺乏正式的敏感性分析**。

**线上结果**：淘宝"猜你喜欢" **+0.35% 交易量**，策略已全量部署。
发布 **AL-GR** 数据集：**140 亿交互 / 2.5 亿物品** + 多模态特征。

> **对我们的启示**：我们在 `rq/eval_sid.py` 里做的三件套（ICR / MSE / LCP）
> 与 FORGE 的目标一致——都是"免训练评估 SID 质量"。
> FORGE 的 `embedding hitrate` 与 `Gini coefficient` 值得作为**第 4、5 个指标**补进来（见 §6.3）。

### 2.3 AdaSID / 快手 — "自适应碰撞处理"（★ 直接命中我们的实测问题）

**问题定义（论文原文批评）**：

> "现有方法主要依赖改进量化或**固定重叠正则（fixed overlap regularization）**，
> 但它们**不能自适应区分某个重叠应该被抑制还是保留**。"

**两阶段框架**：

**Stage 1 — 语义自适应重叠放宽（Semantic-Adaptive Overlap Relaxation）**

对每一对发生 SID 冲突的物品 `(i, j)`：
1. 先看 SID 是否重叠
2. 再看**连续多模态 embedding 的 cos 相似度** `sim_ij`
3. 若 `sim_ij ≥ η` → **判定为语义兼容，不惩罚**（保留共享）

**深度感知阈值（depth-aware）**——冲突越深，要求越严：

| 冲突层级 | 阈值 η | 含义 |
|---|---|---|
| 1 级分类冲突 | 0.18 | 浅层冲突：中等语义邻近即可放行 |
| 2 级分类冲突 | 0.24 | |
| 3 级分类冲突 | 0.30 | 深层冲突：要求严格语义等价 |

> 原文举例：`s1=[10,20,30]` vs `s2=[10,25,35]` 为 1 级冲突；
> `s1` vs `s4=[10,20,35]` 为 2 级冲突；`s1` vs `s3=[10,20,30]` 为 3 级冲突（完全相同）。
> 注意 RQ 的层级不完全等同于多级分类——`[10,20,30]` vs `[10,21,30]`
> 首尾相同、中间不同，也按"两级冲突"处理。

**Stage 2 — 自适应压力分配（Adaptive Pressure Allocation）**

对未被放宽的冲突，惩罚权重 = **空间项 × 时间项**：

```
weight_ij = a_ij (空间) × λ_col(τ) (时间)
```

- **`a_ij`（空间／拥挤度）**：统计冲突签名 `κ_ij` 在 batch 内出现的次数 `c_ij`；
  拥挤度低 → 权重 1；拥挤度高 → 权重 **2~3**
  （即：密集塌缩区域的冲突要往死里拆，稀疏区域不用管）
- **`λ_col(τ)`（时间／训练进度）**：`λ_col(τ) = 1 - (1 - λ_min) · τ`，
  随训练推进**逐渐衰减**（后期把优化重心让给推荐对齐）

**总损失**：

```
L_col_ada = Σ [ (1 - g_ij) × a_ij × λ_col(τ) × margin_loss ]
```
其中 `g_ij` 是 Stage 1 的放宽门（1 = 放行，不惩罚）。

**离线结果**（Toys 数据集，下游统一用 TIGER）：

| Tokenizer | Recall@3 | NDCG@3 | Recall@5 | NDCG@5 |
|---|---|---|---|---|
| RQ-VAE | 0.0164 | 0.0142 | 0.0197 | 0.0161 |
| RQ-KMeans | 0.0193 | 0.0160 | 0.0271 | 0.0187 |
| QuaSID | 0.0195 | 0.0157 | 0.0273 | 0.0191 |
| **AdaSID** | **0.0214** | **0.0175** | **0.0281** | **0.0202** |

→ vs RQ-VAE 基线：**Recall@5 +42.6%**，论文口径"Recall 与 NDCG 平均 +4.5%"（对强基线）。

**线上结果**（快手电商，数千万用户 A/B）：

| 指标 | 增益 |
|---|---|
| GMV | **+0.98%** |
| Orders | +0.91% |
| GPM | +1.16% |
| Overall CTCVR | +0.05pp |
| Scenario-A CVR | +0.05pp |
| Cold-start CVR | +0.08pp |

### 2.4 OneRec / 快手 — "统一生成 + 多模态 tokenization"

- 把召回、排序、解释统一进单一生成模型
- Item 表示：**hierarchical quantization（RQ-Kmeans 或 RQ-VAE）** 压成离散码序列，
  映射进生成模型词表（"itemic tokens"）
- **多模态 tokenization**：从多模态 item embedding 做残留量化
- OneRec-V2 转纯 decoder-only "lazy" 架构 → 训练算力 **-94%**，可扩到 8B+
- RL：GRPO / **ECPO（Early-Clipped GRPO）**、DPO、quantile-based reward shaping
- 多场景扩展：OneMall（电商）/ OneSearch + UniSearch（搜索+推荐统一）/ OneLive（直播）

## 4. 我们当前实现的位置（诚实评估）

**做对的地方**：
- 走了 RQ-VAE 路线 ✔（三家工业界全部选它或 RQ-KMeans，我们的默认选择正确）
- 做了融合消融（4 种模式）✔（PLUM 也做了多模态融合，方向一致）
- 有 SID 免训练评估 ✔（与 FORGE 思路一致）

**明确落后于工业界的三个点**：
1. **融合与量化是两阶段分离的** → PLUM 是端到端联合优化（见 §6.1）
2. **碰撞消解是无差别的 Sinkhorn** → AdaSID 证明应该语义自适应（见 §6.2）
3. **码本是均匀的 256×3** → PLUM 用递减多分辨率，FORGE 说 3×8192（见 §6.4）

## 5. ★ 关键交叉验证：AdaSID 解释了我们 M2 实测到的现象

我们在 M2 用合成数据实测（`.tmp/sidtest`，6000×128，码本 64×64）：

| 指标 | 实测值 |
|---|---|
| 纯 argmin codes 2 层重建 MSE | **0.000875**（与模型 forward 的 0.00087470 吻合 → 算法正确）|
| 碰撞消解后 codes 2 层重建 MSE | 0.001319 |
| **保真度代价** | **ΔMSE +0.000444，保真度降 51%** |
| 被改动的码比例 | **99.2%** |

我们当时的结论是："**Sinkhorn 碰撞消解是用保真度换唯一性**"——
因为 64×64 = 4096 个码 < 6000 物品，数学上不可能唯一，
循环空转 20 轮，Sinkhorn 强行把物品摊到全码本，保真度崩掉。

**AdaSID 给出的正是这个现象的工业级解法**：

> Sinkhorn 消解 = 论文批评的 "fixed overlap regularization"
> —— 对所有碰撞一视同仁地排斥，不管它们语义上是否本该共享。

在 4096 < 6000 这种**码本容量不足**的场景下，
唯一正确解不是"强行拆散所有碰撞"，而是**只拆语义不兼容的那些，语义兼容的允许共享**。
这恰好是我们实测场景里应该做的事。

> 补充：AdaSID 的阈值是 1 级 0.18 / 2 级 0.24 / 3 级 0.30。
> 这可以作为一个**立即可验证的实验**（见 §6.2）。

## 6. 可落地的改进（按 ROI 排序）

### 6.1 【高】把共现对比损失下沉到量化器（对齐 PLUM）

**现状**：我们在 `fuse_embeddings.py` 中用 InfoNCE 训练**融合网络**，
然后冻结融合向量去训 RQ-VAE。
**问题**：量化器只优化重建，不知道"什么对推荐有用"。
**改法**：在 `rq/rqvae.py` 的训练目标里加 `L_con`：
`L = L_recon + L_rq + λ_con · L_con`，
`L_con` 用 `IandS.train.inter` 抽的共现对。

**为什么 ROI 高**：这是论文口径下"把协同信号注入 tokenization"的标准做法，
且**我们已经有了共现对抽取代码**（`load_pairs`），改造成本低。
**预期**：SID 的 LCP / prefix cohesion 应有提升（协同信号使同消费物品靠近）。

### 6.2 【高】碰撞消解改为语义自适应（对齐 AdaSID）

**现状**：`build_sid.py` 用 Sinkhorn 无差别消解所有碰撞 → 实测保真度降 51%。
**改法**（两阶段，直接照 AdaSID）：

```python
# Stage 1: 语义兼容的碰撞 → 放行，不消解
for (i, j) in collided_pairs:
    depth = overlap_depth(sid_i, sid_j)          # 冲突层级
    eta   = {1: 0.18, 2: 0.24, 3: 0.30}[depth]   # 深度感知阈值
    if cos_sim(emb_i, emb_j) >= eta:
        continue          # 语义本就相近，允许共享同一 SID
    # Stage 2: 需要消解 → 权重按拥挤度放大
    a_ij = load_weight(count_in_batch(sid_i, sid_j))   # 1 ~ 3
    resolve(i, j, weight=a_ij)
```

**为什么 ROI 高**：这是**我们实测已经量化出损失**（ΔMSE +51%）的地方，
改造后可以直接用现有 `eval_sid.py` 验证保真度是否回升。
**这是本项目最有可能做出"我们自己的数字"的改进点。**

### 6.3 【中】给 `eval_sid.py` 补 FORGE 的两个免训练指标

**现状**：三件套 = ICR / 重建 MSE / LCP + prefix cohesion。
**补**：`embedding hitrate` + `Gini coefficient`（衡量码本使用均衡度）。
**价值**：Gini 能直接量化"Sinkhorn 是否把物品摊得太均匀"，
与 §6.2 的改进形成闭环验证。

### 6.4 【中】码本结构实验

**现状**：均匀 256×3。
**试**：
- PLUM 式递减：2048 / 1024 / 512
- FORGE 式：3×8192（显存 ×32，本地 4GB 需评估可行性）
**注意**：FORGE 的 `1024_4096_32768` 是**递增**结构，与 PLUM 递减相反，
说明这个自由度**尚无定论**，是我们能做出贡献的地方。

### 6.5 【低】训练范式补齐

工业界已是 **Pre-train → SFT → RL** 三段式。
我们的 UPGRADE_PLAN 已规划 SFT + 双轨 RL（分层奖励 / OPD），方向对齐，
但还停留在计划阶段。

## 7. 面试话术（可直接用）

**Q: 你们的多模态 SID 是怎么做的？**

> 文本走 Qwen3-Embedding-0.6B、图像走 SigLIP，先做融合消融——
> 对比了纯文本、PCA 线性降维、MLP 非线性降维、门控融合四种，
> 用共现对比损失（同用户行为序列内共现的物品对做 InfoNCE）作为监督信号，
> 这样融合向量优化的是"推荐友好度"而不是单纯的模态对齐。
> 融合后统一压到 1024 维再进 RQ-VAE，保证消融时下游量化器完全一致、指标可比。
> 这个设计参考了 YouTube 的 PLUM 的 SID-v2。

**Q: SID 质量怎么评估？**

> 三层免训练评估：uniqueness（ICR / 碰撞率 / per-layer entropy）、
> fidelity（逐层累积重建 MSE / R² / cosine）、
> retrieval structure（LCP + prefix cohesion vs 随机基线）。
> 这个思路和阿里 FORGE 一致——他们也强调 SID 评估不应该依赖昂贵的 GR 训练，
> 并给了 embedding hitrate + Gini 两个指标。

**Q: 碰撞怎么处理？**（★ 最有料的一问）

> 我们实测发现 Sinkhorn 无差别碰撞消解是**用保真度换唯一性**——
> 在码本容量不足时，保真度会掉一半（重建 MSE 从 0.000875 涨到 0.001319，+51%）。
> 后来看到快手 2026 年的 AdaSID 正好解释了这个现象：
> 死板的重叠正则会强行拆散语义上本该共享 SID 的物品。
> 他们的做法是两阶段——先用多模态 embedding 的 cos 相似度判断碰撞是否"语义兼容"，
> 兼容就放行（阈值深度感知：浅层 0.18、深层 0.30），
> 只对语义不兼容的碰撞做消解，且权重按局部拥挤度放大 2~3 倍。
> 线上在快手电商做到 GMV +0.98%。

## 9. 附录 A：两个编码器底座技术档案

> 本节记录我们实际使用的两个编码器的技术细节与实测数字，供复盘与面试引用。
> 所有「实测」数字来自本机 RTX 3050 Ti 4GB 的实际编码运行，非论文引用值。

### 9.1 SigLIP-base-patch16-224（图像塔）

| 项目 | 值 |
|---|---|
| 出身 | Google DeepMind，ICCV 2023 Oral，arXiv:2303.15343（Zhai, Mustafa, Kolesnikov, Beyer） |
| 视觉塔 | ViT-B/16，12 层，hidden 768，patch 16×16，输入 224×224 → 196 patches |
| 文本塔 | 同宽 768，12 头，词表 32,000（English C4 上训的 sentencepiece），最长 16 token |
| 训练数据 | WebLI（仅英文图文对） |
| 官方零样本 | ImageNet 73.4%（B/16 从头训，32 块 TPUv4 × 5 天）；576-patch 变体可达 78.6% |
| 官方检索 | COCO R@1：T→I 49.7 / I→T 67.5（576-patch） |
| 输出 | 768 维，已 L2 归一化，两塔共享同一空间 |
| 本机实测 | dim=768，I&S 覆盖 25,824/25,847 = **99.91%**，858s；VG 覆盖 25,570/25,611 = **99.84%**，732s |

**核心创新 —— 逐对 sigmoid 损失（替代 CLIP 的 softmax InfoNCE）：**

- CLIP 的 softmax 要在整批相似度矩阵上做**全局归一化**：分母是 batch 内全部相似度之和
  → 需要 all-gather 把样本同步到每张卡；显存 O(B²)；损失与 batch size 强耦合。
- SigLIP 把对齐转成**所有图文对组合上的标准二分类**：对角线为正样本、非对角线为负样本，
  逐对算 sigmoid 交叉熵再求和。**不需要看到全 batch** → 可分块（chunked）计算，
  显存从 O(B²) 降到 O(b²)（b 为单卡 batch）。
- 再加**可学习温度 t 与偏置 b**（初始化 log 10 / −10），缓解正样本 1 : N−1 的极端不平衡
  —— 消融显示这个 bias 对稳定训练「至关重要」，不是可选项。
- 副产品结论：对比学习的 batch 收益**快速饱和，32k 就够了**（推到 100 万也几乎没提升）。

**对我们的意义（诚实版）：**
- sigmoid 损失的卖点是**训练效率**，而我们是纯推理（冻结权重，不微调），所以这个优势**我们用不到**。
  选它的真实理由是：① 开箱即用的强图文对齐，冻结当特征提取器就够；
  ② 只占 0.42GB 显存；③ 768 维比 CLIP-L 的 1024 维更省下游开销。
- ⚠️ 局限：SigLIP 的图文对齐是在**通用英文网络图文**上学的，不是电商商品域。
  商品主图里大量存在纯白底 + 包装盒 + 文字特写，与通用 caption 分布有偏。
  我们**没有做任何域适应**——这是当前流水线一个未被验证的假设，后续应做
  「图像塔冻结 vs 轻量域适应」的对照实验。

### 9.2 Qwen3-Embedding-0.6B（文本塔）

| 项目 | 值（带 ★ 的为本机 `config.json` 实测读出） |
|---|---|
| 出身 | 阿里 Qwen 团队，2025-06 发布，Apache 2.0 |
| 基座 | Qwen3-0.6B-Base，经 **LoRA 微调**成双塔 embedding 模型 |
| 架构 | ★ `architectures: Qwen3ForCausalLM` —— **本质是 decoder-only 因果 LM** |
| 层数 / 宽度 | ★ 28 层 / hidden 1024，intermediate 3072 |
| 注意力 | ★ GQA：16 个 Q 头 / 8 个 KV 头；★ `head_dim=128` |
| 词表 | ★ 151,669 |
| 上下文 | ★ `max_position_embeddings = 32768`（原生 32k）；★ RoPE θ=1e6 |
| 其他 | ★ `tie_word_embeddings: true`，★ `torch_dtype: bfloat16` |
| 输出维度 | 1024（MRL 支持 32 ~ 1024 任意截断） |
| 池化 | **last-token pooling**：取最后一层 `[EOS]` 位置的隐状态（需左 padding） |
| 官方评测 | MTEB (Eng) **70.70**；MMTEB 64.33；MTEB-Code 75.41 |
| 本机实测 | dim=1024，I&S 文本均长 711 字符 / token 均 173（中位 175，p95 256）；VG token 均 127（中位 114） |

**三个容易被忽略的设计点：**

1. **`head_dim` 与 `hidden_size / num_heads` 解耦。**
   ★ 实测 `16 头 × 128 = 2048 ≠ hidden 1024`。Qwen3 系列刻意把 head_dim 固定为 128，
   不再等于 hidden/heads（1024/16=64）。写自定义 attention 或算 FLOPs 时若按老公式估会算错一倍。
2. **它是因果 LM，不是双塔编码器。**
   架构标签是 `Qwen3ForCausalLM`，embedding 只是「把最后一层隐状态抠出来」——
   这也解释了为什么必须用 last-token pooling：因果注意力下只有末位 token 能「看见」全部前文。
   官方同时提供 `Qwen3-Reranker` 走**单塔**（输入文本对、输出相关性分数），与 embedding 的**双塔**形成互补。
3. **指令感知（instruction-aware）。**
   query 侧加 `Instruct: {任务描述}\nQuery: {query}`，文档侧不加。
   官方称多数检索场景不加指令会掉 **1%~5%**；多语言场景建议指令用英文写。
   → 我们当前**只做物品侧编码、不加指令**，属于合理用法；但如果将来要编码用户 query，
   必须走 `get_detailed_instruct` 这条路径，否则会白白丢掉几个点。

**训练范式（三阶段，可直接复用到面试回答）：**
① 超大规模弱监督数据对比预训练（用 Qwen3-32B **合成**弱监督文本对，而非社区论坛挖掘）
→ ② 高质量标注数据监督训练
→ ③ **模型融合**（Slerp 球面线性插值）合并多个候选模型，提升鲁棒性。
消融显示：去掉合成数据或去掉模型融合，性能都会掉。

**为什么我们停在 0.6B 而不上 4B/8B：**

| 模型 | MTEB (Eng) | 嵌入维度 | 单卡 4GB 可行性 |
|---|---|---|---|
| Qwen3-Embedding-0.6B | 70.70 | 1024 | ✅ 实测 1.19GB，跑得动 |
| Qwen3-Embedding-4B | 74.60 | 2560 | ❌ fp16 权重即 8GB |
| Qwen3-Embedding-8B | 75.22 | 4096 | ❌ fp16 权重即 16GB |
| 最佳竞品 | 73.30 | — | — |

关键判断：**0.6B 不是最优，是「4GB 卡上唯一能跑的档位」**。
它的 70.70 甚至低于最佳竞品 73.30，这是我们必须诚实承认的差距。
真正的解法不是换更大的编码器，而是 9.1 节提到的**轻量域适应** + 后续 W3 的
「在云端 3090 上换 4B 重编码」——那也是唯一能验证「编码器规模是否是瓶颈」的实验设计。
